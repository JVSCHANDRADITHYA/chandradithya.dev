01
Overview

A control plane
that provisions at scale

SendStores implements a Kubernetes-native control plane to provision, manage, and tear down isolated WordPress + WooCommerce instances on demand. Unlike standard multi-site installations, each store runs as a distinct set of workloads in its own namespace — with a dedicated database, persistent storage, and networking rules.

A Node.js backend orchestrates Helm charts to create ephemeral or permanent store environments without manual intervention, targeting a production-aligned SaaS provisioning pattern. Zero shared runtime state between tenants means each store is hermetically isolated.

02
Architecture

Three-layer design

LAYER 01
Control Plane
Node.js backend accepts POST /stores requests, generates a unique Store ID mapped to a K8s Namespace, and wraps the Helm CLI to execute installs and uninstalls. Redis acts as the single source of truth for provisioning intent and state — no direct K8s API calls from the frontend.
LAYER 02
Data Plane (K8s)
Per store: MySQL StatefulSet with dedicated PVC, WordPress Deployment with a custom wp-cli image, ClusterIP Service, and Ingress rules exposing unique subdomains. Zero shared runtime state between tenants — secrets, volumes, and networking are fully separated at the namespace level.
LAYER 03
Observability
React dashboard polls the backend API — never touches the K8s API directly — displaying real-time store status, provisioning progress bars, per-store URLs, and platform health percentage. Built with Recharts for live provisioning graphs.

Key Features

Production-grade
isolation by default

⬡
Namespace Isolation
Hard K8s namespace isolation per store — secrets, volumes, and networking fully separated. No tenant can touch another's data.
◈
Helm as the Contract
Single Helm chart for all deployments. Environment differences handled via values.yaml only — no duplicate manifests to maintain.
⟳
Automated Lifecycle
Node.js backend handles creation (helm install), state tracking via Redis, and full destruction (helm uninstall) — no manual steps.
⊞
Persistent Storage
Dynamic PVCs provisioned per store for both MySQL data and WordPress content. Data survives pod restarts.
⇌
Ingress-Ready
Auto-configures Nginx Ingress rules exposing each store on a unique subdomain the moment it's created.
✓
Deterministic Bootstrap
Custom WordPress image with wp-cli; post-install exec solves the empty-install race condition for guaranteed first-visit readiness.
04
Engineering Challenge

The Bootstrap Problem

The Problem
Race conditions on first boot
Initial provisioning resulted in WordPress instances showing the Language Selection and Install screens on first visit. Helm Hooks using wp-cli Jobs failed due to race conditions and filesystem mismatches between the Job container and the main WordPress container — the Init Container approach couldn't guarantee the same filesystem and PHP environment as the live site.
The Solution
Two-step deterministic bootstrap
01
Custom Image: Built a WordPress image that includes the wp-cli binary directly — no separate Job container with mismatched filesystems.
02
Post-Install Exec: Backend triggers kubectl exec after the Pod reaches Running state — wp-cli operates on the exact same filesystem and PHP environment as the live site, guaranteeing a fully installed WooCommerce storefront on every first visit.
